# Подслушано РАНХиГС | Волгоград

Telegram-бот для анонимной предложки: обычные студенческие истории публикуются в канале после автоматической проверки, спорные сообщения поступают администратору с кнопками решения.

Python 3.11+, aiogram 3, **PostgreSQL 17+**, asyncpg, python-dotenv. Веб-панели, Redis и платных AI API нет.

## Быстрый запуск в Docker

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите токен и добавьте бота администратором канала с правом публикации сообщений.
2. Администратор должен открыть личный чат с ботом и отправить `/start`. Укажите его числовой Telegram ID в `ADMIN_ID`.
3. Скопируйте `.env.example` в `.env`. Заполните `BOT_TOKEN`, `ADMIN_ID`, `CHANNEL_ID` (например, `-1001234567890` или `@channel_username`). Замените `POSTGRES_PASSWORD` на случайный пароль из латинских букв и цифр (например, `openssl rand -hex 24`).
4. Запустите из каталога проекта:

```sh
docker compose up -d --build
```

Compose запускает PostgreSQL, ждёт готовности базы и запускает бот. `DATABASE_URL` внутри контейнера автоматически собирается из `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, с хостом `db`.

Если PostgreSQL уже есть, укажите готовую строку подключения в `DATABASE_URL` (сохраните параметры SSL от провайдера) и используйте отдельный файл:

```sh
docker compose -f docker-compose.external.yml up -d --build
```

В этом режиме нужны `BOT_TOKEN`, `ADMIN_ID`, `CHANNEL_ID`, `DATABASE_URL`. Переменные `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` не используются. Контейнер получает строку подключения без подмены и не запускает свою базу. Хост в строке должен быть доступен из контейнера; `localhost` внутри него означает сам контейнер. Для логов и перезапуска также добавляйте `-f docker-compose.external.yml` к командам ниже. Боту нужны права создавать таблицы в выбранной базе.

База хранится в именованном томе `postgres_data` и переживает пересоздание контейнеров. `docker compose down` сохраняет том; `docker compose down -v` удаляет данные. Порт PostgreSQL наружу не открыт. При изменении пароля существующей базы нужно отдельно изменить пароль роли PostgreSQL: переменные инициализации действуют только для нового тома.

```sh
docker compose logs -f bot
docker compose restart bot
```

При старте проверяются конфигурация, подключение PostgreSQL, тип канала, права бота и возможность отправить сообщение администратору. Таблицы создаются автоматически. Один процесс polling на токен и одну базу; второй процесс с той же базой блокируется advisory lock PostgreSQL. Бот работает через long polling, открытый входящий порт ему не нужен. [Документация aiogram](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html).

## Запуск без Docker

Установите PostgreSQL 17+, создайте отдельные базу и роль, заполните `.env`. Для запуска на той же машине:

```env
DATABASE_URL=postgresql://ranhigs:YOUR_PASSWORD@localhost:5432/ranhigs
```

Пароль в URL должен быть percent-encoded, если содержит специальные символы. Для удалённой базы используйте защищённое подключение, например `?sslmode=require`.

```sh
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python -m bot
```

Если хостинг просит указать команду запуска, используйте `python main.py` из корня репозитория. Корень сборки также должен быть корнем репозитория, где находятся `main.py`, `Dockerfile` и `requirements.txt`. Docker-образ сам запускает `/usr/src/app/main.py`; при использовании Dockerfile дополнительная команда запуска в панели не нужна.

Ошибка `No module named bot.__main__` означает, что Python загрузил пакет без точки входа. В этом репозитории обе точки входа присутствуют: проверьте ветку `main`, актуальный коммит, корень сборки и пользовательскую команду запуска. Пересоберите образ из свежего исходного кода; если панель продолжает запускать старую команду, замените её на `python main.py`. Сборка Docker проверяет импорт модулей до запуска контейнера.

### Bothost.ru

В настройках репозитория укажите этот Git URL и ветку `main`, включите использование собственного Dockerfile, затем нажмите «Сохранить и пересобрать». Переменные `BOT_TOKEN`, `ADMIN_ID`, `CHANNEL_ID`, `DATABASE_URL` задайте в панели. Docker Compose на хостинге для внешней базы не нужен.

Приложение в образе находится в `/usr/src/app`: BotHost может монтировать свои исходники поверх `/app`, поэтому этот каталог не используется для запуска. Это соответствует [рекомендации хостинга](https://bothost.ru/docs/common-errors). В новой сборке должна появиться строка `RANHIGS image entry point verified: /usr/src/app/main.py`. Если её нет и ошибка всё ещё относится к `python -m bot`, проверьте выбор собственного Dockerfile и получение свежего коммита: одного перезапуска старого контейнера недостаточно.

В PowerShell активация: `.\.venv\Scripts\Activate.ps1`. Рабочий каталог — корень проекта. Дальнейшие запуски: `python -m bot`. На VPS процесс можно запускать через systemd с `WorkingDirectory` на каталог проекта и `ExecStart` на `.venv/bin/python -m bot`.

## Пользовательский сценарий

`/start` показывает приветствие и кнопку «✍️ Отправить публикацию». Можно сразу прислать текст, emoji и переносы строк. Фото, документы, видео и голосовые не принимаются. Проверка не пересылает оригинал: в канал отправляется новый пост с заголовком, текстом и `#подслушано`. Форматирование пользователя экранируется; скрытые ссылки из Telegram entities не переносятся и требуют проверки.

`/privacy` объясняет, какие данные доступны владельцу. Читатели не получают ID, имя или профиль автора из метаданных бота. Администратору доступны текст и Telegram ID для модерации и блокировок; абсолютная анонимность перед владельцем не обещается. Если сам текст содержит имя или контакты, он должен пройти ручную проверку перед публикацией.

## Управление

Все команды и кнопки модерации проверяют `ADMIN_ID` и работают только в личном чате.

| Команда | Действие |
| --- | --- |
| `/pending [страница]` | Очередь по 5 заявок, повторно показывает карточки с кнопками |
| `/stats` | Всего, авто/ручные публикации, отклонённые, очередь, неизвестные отправки, блокировки, последние 24 часа |
| `/ban USER_ID` | Блокирует автора, отклоняет его ожидающие заявки |
| `/unban USER_ID` | Снимает блокировку |
| `/autopublish on` | Автопубликация новых текстов со статусом `safe` |
| `/autopublish off` | Все новые заявки поступают на модерацию |
| `/resolve ID MESSAGE_ID` | Подтверждает уже опубликованный пост после отправки с неизвестным результатом |
| `/retry ID` | После проверки отсутствия поста возвращает неизвестную отправку в ручную очередь |
| `/purge_rejected` | Удаляет отклонённые заявки старше срока хранения |
| `/help_admin` | Справка |

Кнопки карточки: «Опубликовать», «Отклонить», «Заблокировать автора». Решение обновляет заявку и уведомляет автора, если бот может ему написать. После обработки кнопки карточки удаляются. Старые копии карточек защищены проверкой статуса в базе. Блокировка не отменяет отправку, уже начатую до её применения.

Настройка `/autopublish` сохраняется в PostgreSQL. `AUTO_PUBLISH` из `.env` используется только при первом создании настройки; затем управлять ей нужно командой. Включение не публикует накопленную очередь автоматически.

## Модерация и ограничения

В `moderation_rules.json` находятся категории, корни и фразы, регулярные выражения, исключения и разрешённые хосты ссылок. Изменения загружаются при перезапуске; в Docker после изменения файла пересоберите образ.

- `safe`: правила не нашли признаков риска; разрешена автопубликация, если она включена.
- `review`: требуется оценка администратором.
- `blocked`: найдены признаки серьёзного риска; автопубликация запрещена, окончательное решение принимает администратор.

Проверки включают NFKC, регистр и `ё`, невидимые символы, похожие латинские буквы, некоторые цифровые подмены, повторяющиеся буквы и разделители внутри слов. Отдельно проверяются контакты, адреса, идентификаторы, полные имена, ссылки, угрозы, травля, дискриминация, интимные сведения и обвинения. Причины видит только администратор. Обычные вопросы и описание неприятного происшествия без рискованных деталей не блокируются по одному факту жалобы.

Автоматически разрешены только HTTPS-ссылки на точные хосты из `allowed_link_hosts` без параметров перенаправления и рефералов. Остальные ссылки, личные профили и скрытые ссылки передаются на ручную проверку; администратор может одобрить их. Страницы по ссылкам бот не загружает. Словарь и regex не понимают смысл надёжно и не гарантируют обнаружение всех опасных сообщений. Для предварительной проверки правил на своём канале используйте `/autopublish off`.

| Переменная | По умолчанию |
| --- | --- |
| `MIN_TEXT_LENGTH` / `MAX_TEXT_LENGTH` | 10 / 3000 символов |
| `RATE_LIMIT_COUNT` | 3 заявки |
| `RATE_LIMIT_WINDOW_SECONDS` | 600 секунд |
| `MIN_SUBMISSION_INTERVAL_SECONDS` | 15 секунд |
| `DUPLICATE_WINDOW_SECONDS` | 86400 секунд, повтор текста среди всех авторов |
| `REJECTED_RETENTION_DAYS` | 30 дней |
| `MAINTENANCE_INTERVAL_SECONDS` | 60 секунд |
| `MODERATION_RULES_PATH` | `./moderation_rules.json` |
| `LOG_LEVEL` | `INFO` |

Лимит Telegram проверяется также в единицах UTF-16 с учётом оформления, поэтому большое количество emoji может потребовать сократить текст. Лимиты и дубликаты проверяются в одной транзакции с PostgreSQL advisory locks; превышение лимита не добавляет автора в blacklist. После перезапуска ограничения сохраняются.

## Восстановление без повторной публикации

Рабочие статусы заявки: `pending → publishing → published`, `pending → rejected`, а при неоднозначном результате — `uncertain`. `moderation_status` (`safe/review/blocked`) хранится отдельно.

Переход в `publishing` атомарный; конкурирующие кнопки не начинают вторую отправку. Ошибка, явно возвращённая Telegram (например, отсутствие прав или 429), возвращает заявку в `pending` для ручного повторения. Таймаут, разрыв соединения или ошибка сервера переводят её в `uncertain` и запрещают повторную отправку. Если процесс остановился между отправкой и записью результата, при старте `publishing` также становится `uncertain`.

Владелец сначала проверяет канал. Если пост уже появился, отправляет `/resolve 123 456`, где `456` — ID реального сообщения в канале (последнее число ссылки на пост). Команда записывает подтверждение владельца; Telegram Bot API не предоставляет чтение истории канала для автоматического поиска поста. Если пост точно отсутствует, `/retry 123` возвращает карточку в очередь; затем нажмите «Опубликовать». Слепых автоматических повторов нет.

Обычные ожидающие заявки после перезапуска остаются в очереди, без автоматического массового одобрения. Фоновая задача повторяет доставку неотправленных карточек администратору. Сбой между доставкой карточки и её отметкой в базе может дать вторую карточку; действие по обеим остаётся защищено от повторной публикации. Уведомления автору отправляются по возможности и при недоступности пользователя не откатывают публикацию.

## Данные и резервные копии

Схема создаёт `submissions`, `banned_users`, `settings`; ID Telegram и заявок — `BIGINT`, даты — `TIMESTAMPTZ`, причины — `JSONB`. Все значения SQL передаются параметрами `$1…`; работа с подключениями — через пул asyncpg. [Документация asyncpg](https://magicstack.github.io/asyncpg/current/usage.html).

В логах приложения нет текстов заявок, Telegram ID отправителей, токенов и строки подключения; для диагностики ошибок выводится имя класса ошибки, а при проверке Telegram — также название запроса и распознанная безопасная причина, например `getChat(channel): chat not found`. Исходный ответ и запрос Telegram в лог не записываются. `.env`, тестовые бинарники и данные не попадают в Git или Docker-образ. Контейнер бота запускается без root.

Отклонённые заявки автоматически удаляются из рабочей базы по сроку; статистика отражает только оставшиеся записи. Одобренные заявки и blacklist хранятся до удаления владельцем. Удаление из PostgreSQL не удаляет копии из чата администратора, канала, WAL и резервных копий: их сроки и очистку обеспечивает владелец инфраструктуры. Не передавайте доступ к базе посторонним.

Резервная копия (Linux):

```sh
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > backup.dump
```

## Проверки

Модульные тесты запускаются без Telegram и PostgreSQL:

```sh
python -m unittest tests.test_moderation -v
```

Для интеграционных тестов нужна **отдельная тестовая база PostgreSQL**: тесты очищают таблицы в `TEST_DATABASE_URL`. Не указывайте рабочую базу.

```sh
export TEST_DATABASE_URL=postgresql://test:test@localhost:5432/ranhigs_test
python -m unittest discover -s tests -v
```

PowerShell: `$env:TEST_DATABASE_URL='postgresql://test:test@localhost:5432/ranhigs_test'`. Без переменной интеграционные тесты явно отмечаются как пропущенные. Telegram в тестах заменён mock-объектом; реальные публикации не отправляются.

```sh
pip install ruff
ruff check .
ruff format --check .
```

GitHub Actions запускает PostgreSQL 17, модульные и интеграционные тесты, линтер и сборку Docker. Проверяются обходы словаря, исключения, контакты и ссылки, публикация и модерация, блокировки, конкурентные лимиты и нажатия, сбои доставки, восстановление очереди и очистка данных.
